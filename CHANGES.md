## Batch 4 — Deploy 3 (render path, dedupe, guard)

Applied 2026-08-28, commit `1840af8`. Three fixes, all downstream of the
verification above.

### 1. `situations/[slug]` was never revalidating

The route had no `revalidate` export, so it was prerendered once at build time
and never again. This is not specific to Deploy 2 — **every** Sanity edit to a
situation page has waited silently on the next deploy to appear. `blog/[slug]`
has carried `revalidate = 3600` all along, which is exactly why the same
deploy's two blog edges went live inside the hour and the other 25 did not.

Now `export const revalidate = 3600`, matching `blog/[slug]`. Build output
confirms it: `● /situations/[slug]   1h   1y`.

`TEMPLATE_REVISION` bumped 2026-08-24 → 2026-08-28 (Hard Rule 13): the pages
now render content the build-time HTML never had.

### 2. Per-target idempotency in `batch4-deploy2.mjs`

The guard was per-SOURCE: it skipped a source only when *every* target in its
paragraph was already linked. The inherited hub's S2 paragraph had 2 of 5
already linked by an older script, so the all-or-nothing test never fired and
the paragraph was written whole, duplicating both.

It is now per-TARGET. An already-linked target keeps its sentence but loses its
link mark, so the prose stays grammatical and no second link is created; the
running set is extended as the run writes, so two paragraphs on one field
cannot duplicate each other either. `--self-test` replays the PLAN against this
deploy's own backup — the exact pre-deploy state that produced the bug — and
asserts 25 links and exactly 2 downgrades.

### 3. The two duplicates removed from the inherited hub

`scripts/batch4-deploy2-dedupe.mjs`, backup
`backups/batch4-deploy2-dedupe-2026-08-28T14-50-18-072Z.json`.

Google credits the FIRST anchor per target, so the duplicates handed the signal
to the older anchors and the query-aligned S2 anchors counted for nothing —
the opposite of what those two hand-off edges are for. Removed:

| removed anchor | → | surviving anchor |
|---|---|---|
| selling an inherited property in Allentown PA | `/blog/sell-inherited-house-allentown-pa` | selling an inherited house in Allentown |
| selling an inherited house in Reading, PA | `/blog/sell-inherited-house-reading-pa` | selling an inherited house in Reading |

The enclosing blocks were deleted, not just the marks: each older paragraph
existed only to carry its link ("...our guide to X walks through the local
process step by step"), and unwrapping would leave a sentence promising a guide
it does not link. Deploy 2's paragraph says the same thing and links both.
`problemDescription` went 9 blocks / 9 links → 7 / 7.

### Verified after the rebuild (2026-08-28, ~100s after push)

Checked with the anchor-inside-`<a>`-with-matching-href test, not a substring
match.

- **27/27 edges rendered**, including all **25/25** situation-side ones.
  `/situations/*` came back `x-vercel-cache: PRERENDER age=0s`.
- **No duplicates left on the hub:** each owner is linked exactly once in the
  body, by the S2 anchor.
- **Sitemap: 11/11** affected URLs now carry `2026-08-28`; 64 URLs, none undated.

One consequence of the bump worth recording: `TEMPLATE_REVISION` is a single
global floor, so all **53** template-rendered URLs now read 2026-08-28 — the 21
location pages and every blog post included, none of which changed. That is
the constant's known coarseness and the price Hard Rule 13 accepts; it is why
it must not be bumped for content-only deploys.

### Known gap

`locations/[slug]` has the same missing `revalidate` and the same latent
staleness. Not fixed here — it wants its own deploy and attribution window.
`/sitemap.xml` is also fully static, so it refreshes on deploy rather than on a
Sanity edit.
